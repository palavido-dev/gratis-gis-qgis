feat(edit): push QGIS edits to a portal-backed layer (Phase 4)

Adds an end-to-end edit-push pipeline so a user editing a layer
that came from a GratisGIS portal (OAPIF source) can save those
edits back without round-tripping through OAPIF's WFS-T (which
not every portal exposes).

Pipeline:

  1. Push-edits dialog lists vector layers in the project whose
     source URI we recognize as a portal OAPIF endpoint.
  2. Walks `editBuffer()` for adds, changed geometries, changed
     attributes, and deletions. Each becomes one EditedFeature.
  3. The pure-Python planner in edit/sync.py turns the buffer
     into an ordered SyncOp list:
       - creates first, then updates, then deletes
       - co-occurring geom + attr edits to the same portal id
         merge into one PATCH (halves round-trips)
       - delete-after-update drops the update (avoids 404)
       - update or delete on a feature with no portal id is
         skipped with a fixable reason
       - empty creates are skipped (no-op POST)
  4. The dialog shows the plan summary + per-op listing, then
     executes one HTTP call per op against the new
     FeaturesEndpoint (POST features, PATCH features/:fid,
     DELETE features/:fid).

The planner stays pure-Python so the rules above are exercised by
16 dedicated tests covering ordering, merging, delete-supersedes,
skip reasons, and edge cases. Six more tests pin the
FeaturesEndpoint wire shape (globalId alias, geometry-absent vs
geometry-null semantics, partial PATCH).

Full suite: 180 pass (68 client + 112 plugin).
